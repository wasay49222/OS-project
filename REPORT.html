Virtual Switch Project Report

Operating Systems · Fall 2026 · Wasay

Project and thread design

The project implements a software network switch in C on Linux. Hosts connect to the switch over TCP, one connection per switch port. Each frame has a 17-byte header containing the payload length, source and destination MAC addresses, VLAN number, and priority, followed by the payload. The switch reads and writes complete frames even when TCP splits data across multiple operations.

The main switch thread accepts connections and assigns available ports. Separate worker threads handle each active port, timers, signals, admin commands, and log output.

The separate host program has a main thread for keyboard input and a receiver thread for frames from the switch. The separate swctl process sends admin commands over a UNIX socket and reads counters from shared memory.

Forwarding and Tier 2 features

A receiver validates each frame, learns its source MAC address, and looks up the destination by MAC address and VLAN. Known unicast frames go to the learned port; broadcasts and unknown destinations are copied to eligible ports. Packet reference counting lets those queued copies share one frame allocation. Each priority class has a bounded queue, with a 64-frame total limit per port. Senders use a 5:3:1 high-to-normal-to-low schedule, and a low-priority frame waiting more than 200 ms is selected early so it does not wait indefinitely.

A token bucket can limit each port’s output rate. A timer refills tokens every 100 ms, and a sender waits on a timed condition variable when it has no token. Access ports are assigned one VLAN; trunk ports keep the frame’s VLAN and carry traffic for all VLANs. Admin commands can mirror port traffic to a sniffer queue, change VLANs, clear the MAC table, or shut down and reopen ports while the switch is running.

Locks, shared state, and lock order

The switch uses small locks around the data each thread shares. Condition variables use the associated queue or timer mutex. The free-port semaphore tracks available connections. Atomic values are used for counters and the stop flag where a separate lock is not needed.

LockData it protects
Port table mutexPort state, active socket assignment, VLAN/trunk settings, mirror destination, and shutdown state.
One output-queue mutex per portQueue contents and positions for the three priority classes, timestamps, queue length, and closed state. Its condition variable wakes the sender.
One rate mutex per portThat port’s configured rate and available tokens.
One mutex per MAC bucketEntries in that hash-table bucket, including address, VLAN, port, and last-seen time.
MAC eviction mutexSerializes selection and removal when the table reaches its size limit; it is taken before one bucket mutex.

Shared statistics mutexPer-port frame-in, frame-out, dropped, and mirrored counters. It is process-shared so swctl can read the same counters.
Timer mutexWait and wakeup coordination for the aging and rate-timer threads.
Log queue mutexMessages, queue positions, and shutdown state for the logger. Producers try the lock and skip a message if it is busy or full.
Host output mutexPrevents the host’s input thread and receive thread from mixing terminal output.

Lock order used

  1. When more than one lock is needed, the port table lock comes before an output queue, rate lock, or shared statistics lock.
  2. An output queue lock may be followed by its packet reference lock when adding or releasing a queued packet, or by its rate lock while checking a token. No path takes the port table lock while holding a queue or rate lock.
  3. The MAC eviction lock comes before one MAC bucket lock. Bucket locks are not nested, and MAC operations do not acquire the port table lock.
  4. The timer and log queue locks are used on their own; the timer releases its lock before visiting port queues and rate limits.

Following this order prevents two threads from waiting on each other in opposite orders. In particular, port reconfiguration and forwarding take the port table lock before the related port data, while MAC learning uses only its bucket and eviction locks.

Signals and clean shutdown

The main thread blocks SIGINT, SIGHUP, and SIGUSR1 before starting workers. A dedicated thread waits for these signals with sigwait. SIGINT closes listeners and active sockets, wakes workers, joins the service threads, and releases resources. SIGHUP reloads the selected configuration file. SIGUSR1 writes the current MAC table to mac_table.dump. SIGPIPE is ignored so a vanished host becomes a normal failed socket write instead of terminating the switch.

Testing and one bug fixed

make check builds the project with strict compiler warnings and runs protocol, forwarding, and lifecycle tests. The checks cover fragmented frames, partial writes, broadcast and learned unicast, slow receivers, disconnect and port reuse, the port limit, MAC moves and aging, least-recently-used eviction, and port security.

Tier 2 network tests cover priority scheduling and low-priority aging, token-bucket rate limiting, VLAN isolation, trunk forwarding, mirroring, config reload, admin commands, port shutdown and restart, shared counters, the stats watch command, signal-triggered MAC dump, and timestamped log output. The Tier 2 network tests also ran under Valgrind and ThreadSanitizer. GCC’s static analyzer was run on the switch and swctl sources.

Bug found during development

GCC’s static analyzer found a path where a client socket could be closed twice if port reservation failed. The accept loop remained responsible for closing a rejected client, while the reservation failure path could also close it. Closing the same descriptor twice is unsafe because the operating system may reuse its number for another socket in between. The fix left socket ownership with the accept loop on failure, so each rejected client is closed once. The integration and connection-reuse checks passed after the change.
